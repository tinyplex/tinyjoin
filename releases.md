<p>This is a reverse chronological summary of TinyJoin releases and their public compatibility boundaries. Every entry states what upgrading to it requires, so check the entries between the version in use and the target before upgrading. A release that needs no action says so explicitly.</p><h2 id="v0-4-0">v0.4.0</h2><p><strong>Persistent storage breaks compatibility with v0.3.0 and earlier.</strong> v0.4.0 introduces page format 3, which stores each row as packed binary columns rather than as JSON text, and encodes keys so that they sort in the same order SQL compares their values. Rows take less space, a query can read the columns it needs without parsing the rest of the row, and <code>ALTER TABLE ... ADD COLUMN</code> no longer rewrites every existing row.</p><p>v0.1.0 through v0.3.0 use page format 2. Opening a page format 2 database with v0.4.0 fails with <code>UNSUPPORTED_PAGE</code>, and so does opening a page format 3 database with an earlier release. There is no automatic migration, and changing the OPFS name does not copy existing data.</p><ul><li>For data that can be reconstructed, use a new OPFS namespace, for example change <code>opfs://my-app-v2</code> to <code>opfs://my-app-v3</code>, and rebuild the database. The old namespace remains intact.</li><li>To retain existing data, export the application&#x27;s known tables using a client pinned to <code>tinyjoin@0.3.0</code> before upgrading. Create the schema in a new namespace with v0.4.0, import rows with parameterized statements, and verify the data before retiring the old database. TinyJoin does not yet provide a general database export or migration API.</li><li>New apps generated by create-tinyjoin v0.4.0 target <code>tinyjoin@^0.4.0</code> and use a <code>-db-v3</code> storage name. Updating the generator does not migrate applications it generated previously.</li></ul><p>In-memory databases, including every <code>tinyjoin/node</code> database, are unaffected.</p><p><strong>Object rows now list their columns in field order.</strong> A row&#x27;s keys follow the result&#x27;s <code>fields</code>, as in PostgreSQL, so <code>SELECT title, id</code> returns rows whose first key is <code>title</code>, and a changed key lists a composite primary key&#x27;s columns in the order the key declares them. Earlier releases sorted both alphabetically. Code that reads a row or key by column name is unaffected; only code that depends on key order, such as <code>Object.keys(row)</code> or <code>JSON.stringify(row)</code>, sees a difference.</p><p><strong>The Worker protocol version moves from 8 to 10.</strong> <a href="https://tinyjoin.org/api/tinyjoin/classes/lifecycle/client/"><code>Client</code></a> and Worker ship together and are upgraded together by a normal install, so this affects only a deployment that pins or caches a Worker file independently of the client bundle. A mismatched pair fails cleanly with <code>PROTOCOL_MISMATCH</code>, and tabs running different releases fail with <code>DATABASE_VERSION_MISMATCH</code>, rather than misreading each other&#x27;s results.</p><p><strong>Numbers keep every bit.</strong> Numbers in JSON values and SQL text are now read with correct rounding. Earlier releases read about one in ten numbers that need all 17 significant digits, such as many results of <code>Math.random()</code>, as a neighboring value. In v0.3.0 and earlier, a row holding one could then not be read at all: reading it failed with <code>PAGED_STORAGE_CORRUPT</code>, because the row no longer matched its stored text.</p><p>This release is also much faster. In the <a href="https://tinyjoin.org/guides/benchmarks/">comparative benchmarks</a>, most workloads in v0.3.0 took 10 to 1,400 times as long as the faster of SQLite and PGlite. None now takes as much as twice as long, and reading every row, <code>LIKE</code> scans, <code>GROUP BY</code>, joins, building indexes, and committing a single insert are quicker than in either.</p><ul><li>Updates, upserts, and deletes inside a transaction no longer slow down as the transaction grows. Each statement is checked against running totals rather than the whole write set, so a thousand of them take about 50 ms rather than more than half a minute.</li><li>Comparisons, <code>BETWEEN</code>, and <code>LIKE</code> patterns that start with literal characters read a range of an index or of the primary key, rather than every row. An aggregate that reads only the index&#x27;s columns is answered from the index alone. See <a href="https://tinyjoin.org/guides/sql-compatibility/#constraints-and-indexes">constraints and indexes</a> for when a range is used.</li><li>Joins find each table&#x27;s matching rows by key lookup, through an index, or in a hash table, rather than comparing every pair of rows. The join budget now counts the rows each lookup actually returns, so a join is never rejected because the Cartesian product of its tables is large.</li><li>A query ordered by the leading primary-key columns reads rows in key order and stops at its <code>LIMIT</code>, rather than collecting and sorting every match, so it is no longer held to the limit on ordered matching rows. Inside a transaction that has changed the table, it still sorts.</li><li>Scans read only the columns a statement uses, straight from the stored row, and so does a statement that finds its row by primary key.</li><li>Each row a statement writes is planned, checked, and measured once. A transaction keeps the rows it stages as the encoded records its commit writes, rather than as maps it copies and encodes again at commit, and reads them in place, as it does stored rows.</li><li>Writes apply each statement&#x27;s rows to each B-tree in one pass, and index builds sort their entries first. A commit writes each page once, a run of consecutive pages with a single storage call, and makes them durable with one flush rather than three. Its superblock records a fingerprint of the pages it wrote, so reopening after an interrupted commit returns to the last complete one.</li><li>Rows travel from the engine to the page as JSON text, which only the page parses, rather than as objects built one property at a time and then copied between threads. A point query takes about a quarter less time, and reading 10,000 rows well under half. A statement that publishes nothing, such as a read or a statement inside a transaction, passes the rest of its result through the Worker as text too, and point statements take 4 to 7% less time.</li><li>On the tab that owns a database, statements reach the engine as calls rather than as messages checked again at every layer.</li><li>A plain <code>INSERT</code> plans each row straight into the record its commit writes, rather than into a map that staging encodes again. So does an <code>UPDATE</code> that leaves each row&#x27;s key in place: it rewrites the stored record, keeping the bytes of every column it does not assign, and 1,000 updates by key take about a tenth less of the engine&#x27;s time. A single-row upsert rewrites the stored row it conflicts with the same way.</li><li>Staging a single-row statement no longer copies the transaction&#x27;s bookkeeping, and each statement&#x27;s request and result are checked, and its result read, with less work on both sides of the Worker. Point inserts, updates, and deletes in a transaction take 5 to 10% less time.</li><li>Scans take each leaf&#x27;s rows straight from the copy of the leaf they hold, checking the tree only as they move between leaves, and read an inline cell and an integer column without the general decoders. A range aggregate over 10,000 rows takes about a quarter less time in the browser.</li><li>A statement&#x27;s changed rows are kept in the order its scan finds them, rather than sorted into maps as they arrive, so deleting 8,000 rows takes about a fifth less time. A <code>DELETE</code> outside a transaction also plans each row by its stored key, rather than as a map of its key columns, which takes a further fifth off.</li><li>A result&#x27;s and a commit&#x27;s changed keys are ordered and deduplicated by their encoded keys, rather than by the JSON text of each, so each table&#x27;s keys are listed in primary-key order: earlier releases listed <code>{&quot;id&quot;: 10}</code> before <code>{&quot;id&quot;: 9}</code>. They are kept as rows of values rather than a map for each key. Inserting 10,000 rows 200 at a time takes a tenth less of the engine&#x27;s time, and a write by primary key 3% less.</li><li>Inside a transaction that has changed a table, a scan finds the rows the transaction replaced leaf by leaf, rather than comparing every row&#x27;s key with the next staged one, and an integer column is compared with integer bounds as integers. A transaction&#x27;s 100 range <code>UPDATE</code>s take a fifth less of the engine&#x27;s time, and 100 range aggregates about a tenth less.</li><li>Writing a page stores each cell&#x27;s fixed-size header and slot directly, rather than copying them a few bytes at a time, and an index key copies text whole. Creating two indexes over 10,000 rows takes 8% less time.</li><li>A commit checksums the zero bytes that fill most of each page 256 at a time, where it read them one at a time, and encodes less besides, writing its allocation bitmap and superblock straight into their pages. Committing a single insert takes over a third less of the engine&#x27;s time, and pages read back from storage are checked faster too.</li><li>Each superblock carries the allocation bitmap for the first 123 MB of the database in the rest of its page, and a commit writes the bitmap&#x27;s other pages only when it changes them, where it rewrote three bitmap pages every time. A commit to a smaller database writes its data pages and its superblock and nothing else: committing a single insert takes about 5% less time with OPFS.</li><li>A write transaction looks for free pages 64 at a time, rather than one at a time from the start of the file, and a commit visits only the cached pages it wrote or freed, rather than every page in the cache. A commit&#x27;s cost now grows much more slowly with the size of the database: committing single inserts into a 100,000-row table takes under half the engine&#x27;s time it did.</li><li>Several of the engine&#x27;s small collections are kept in vectors rather than B-tree maps, whose code is compiled anew for each type they hold, which took about 15 KiB off the compressed engine. Its hash maps and sets share one quick hash rather than SipHash, whose resistance to colliding keys needs random keys that WebAssembly without a host source of randomness never gave it, and four sets that needed no hashing became vectors: 3 KiB more. The catalog&#x27;s tables and indexes, and the keys a write reports, took 5 KiB more.</li><li>Once per page, <a href="https://tinyjoin.org/api/the-essentials/using-a-database/create/"><code>create</code></a>() also starts a short-lived second Worker that runs the engine&#x27;s common statements on a scratch in-memory database for about a tenth of a second, and then exits. Chromium compiles WebAssembly one function at a time, as each is first called, and Workers running the same module share what either compiles, so a database&#x27;s first statements of each kind no longer wait for their code to compile. See <a href="https://tinyjoin.org/guides/custom-workers/">custom Workers</a>.</li></ul><p>The compressed download is now 302 KiB, up from 295 KiB in v0.3.0.</p><h2 id="v0-3-0">v0.3.0</h2><p>This release closes some of the most commonly encountered gaps in the <a href="https://tinyjoin.org/guides/sql-compatibility/">SQL dialect</a>. Each form is new syntax that was previously rejected, so an existing statement keeps its meaning.</p><p><code>BETWEEN</code> and <code>NOT BETWEEN</code> are accepted wherever a <code>WHERE</code> clause is, including in aggregates, joins, <code>UPDATE</code>, <code>DELETE</code>, and prepared statements. <code>price BETWEEN $1 AND $2</code> means exactly <code>price &gt;= $1 AND price &lt;= $2</code>, with the same type checking and <code>NULL</code> behavior as those two comparisons, and it is inclusive at both ends. There is no <code>SYMMETRIC</code> form, so a range whose bounds are reversed matches nothing rather than being swapped.</p><p>A single-table <code>SELECT</code> can now rename its columns with <code>AS</code>, as aggregate and join queries already could: <code>SELECT id AS task_id, title FROM tasks</code>. The alias becomes the result field name, <code>ORDER BY</code> can refer to it, and one column may be returned under several names. As in PostgreSQL, an <code>ORDER BY</code> name matches an output alias before a source column of the same name. Output names must still be distinct.</p><p><code>SELECT DISTINCT</code> removes duplicate rows from a single-table or join projection, which is especially useful for collapsing the rows a many-to-many join multiplies, as in <code>SELECT DISTINCT tag.name FROM post_tags JOIN tags AS tag ON post_tags.tag_id = tag.id</code>. <code>NULL</code>s compare as equal to one another, and <code>LIMIT</code> and <code>OFFSET</code> count distinct rows. As in PostgreSQL, <code>ORDER BY</code> must name projected columns. The projection must list its columns explicitly and cannot contain JSON columns or aggregates, and <code>DISTINCT ON</code> and aggregate <code>DISTINCT</code>, such as <code>COUNT(DISTINCT column)</code>, remain unsupported. A column named <code>distinct</code> remains usable.</p><p><code>INSERT ... ON CONFLICT</code> makes an upsert one atomic statement rather than an <code>UPDATE</code> followed by a conditional <code>INSERT</code> inside a transaction, which held every tab sharing the database for the duration. <code>ON CONFLICT (id) DO NOTHING</code> skips conflicting rows, and <code>ON CONFLICT (id) DO UPDATE SET value = EXCLUDED.value</code> rewrites the stored row. The target is the primary key or the columns of one unique index, and <code>DO NOTHING</code> may omit it to treat every unique constraint as an arbiter. Rows are handled one at a time as in PostgreSQL, so a statement that would update the same row twice fails with <code>CONSTRAINT_VIOLATION</code>. <code>SET</code> accepts literals, parameters, <code>DEFAULT</code>, and <code>EXCLUDED</code> columns, but cannot read the existing row or change its primary key, and <code>DO UPDATE ... WHERE</code> is not supported. <code>RETURNING</code>, the row count, and changed keys include only inserted and updated rows, so a statement that skips every row reports no change. See <a href="https://tinyjoin.org/guides/sql-compatibility/#upserts">upserts</a>.</p><p><code>LIKE</code>, <code>ILIKE</code>, and their <code>NOT</code> forms match a text column against a pattern in which <code>%</code> matches any run of characters and <code>_</code> exactly one, so a search box no longer has to filter rows in JavaScript: <code>WHERE title ILIKE $1</code> with <code>&#x27;%&#x27; + term + &#x27;%&#x27;</code>. Backslash escapes a literal <code>%</code> or <code>_</code> unless an <code>ESCAPE</code> clause names another character, and a pattern that ends in its escape character is rejected. A search term from user input should have its own <code>%</code>, <code>_</code>, and backslash characters escaped before being wrapped in wildcards. <code>ILIKE</code> folds only ASCII letters, as PostgreSQL does under the C locale, which is consistent with TinyJoin&#x27;s code-point ordering, so <code>&#x27;É&#x27; ILIKE &#x27;é&#x27;</code> is false. Pattern matching always scans candidate rows rather than using an index.</p><p><strong>Upgrading from v0.2.0 needs no action.</strong> Install, rebuild, and redeploy. The Worker protocol stays at version 8 and the page format stays at format 2, so an existing database opens with no migration and no OPFS namespace change. The new syntax was previously rejected, so statements that already worked keep their results.</p><p>The engine is now built with Rust 1.98.1 rather than 1.91.1. That more than offsets the new SQL, so the compressed WebAssembly engine is about 4 KiB smaller than in v0.2.0.</p><h2 id="v0-2-0">v0.2.0</h2><p>Subscriptions and statement results now report <strong>which rows changed</strong>, not only which tables. A <a href="https://tinyjoin.org/api/tinyjoin/interfaces/subscriptions/tableschangedevent/"><code>TablesChangedEvent</code></a> and every <a href="https://tinyjoin.org/api/tinyjoin/interfaces/query-results/results/"><code>Results</code></a> carry a <code>keys</code> map of table name to the primary keys that changed, so a listener can refresh individual rows instead of re-reading a table. Keys are reported for writes from any connected <a href="https://tinyjoin.org/api/tinyjoin/classes/lifecycle/client/"><code>Client</code></a>, which makes a change made in another tab resolvable to individual rows. See <a href="https://tinyjoin.org/guides/transactions-and-changes/#refreshing-individual-rows">refreshing individual rows</a>.</p><p>Reporting is a bounded best effort, and the changed-table list stays authoritative. A table appears in <code>keys</code> only when every key it changed fits the bound of 1,000 keys per table; a table that changed more rows is absent rather than partially listed, so an absent table means its rows cannot be named and must be re-queried. <code>keys</code> is always empty alongside <code>reset: true</code>. Code that assumes keys are present will silently miss large writes, so handle the absent case.</p><p><strong>The Worker protocol version moves from 7 to 8.</strong> <a href="https://tinyjoin.org/api/tinyjoin/classes/lifecycle/client/"><code>Client</code></a> and Worker ship together and are upgraded together by a normal install, so this affects only a deployment that pins or caches a Worker file independently of the client bundle. A mismatched pair fails cleanly with <code>PROTOCOL_MISMATCH</code> rather than misreading a result. Applications using <a href="https://tinyjoin.org/api/vite/functions/offline/tinyjoinoffline/"><code>tinyjoinOffline()</code></a> are unaffected: the plugin revisions both files by content, so a rebuild replaces them together.</p><p><strong>Upgrading from v0.1.0 needs no action.</strong> Install, rebuild, and redeploy. Persistent storage is unchanged: the page format remains format 2, so an existing database opens with no migration and no OPFS namespace change. The <code>keys</code> field is additive, so application code that ignores it behaves exactly as it did before.</p><p>Grouped and aggregate queries now use a secondary index when their predicate supplies every column of one, instead of always scanning the table. <a href="https://tinyjoin.org/api/tinyjoin/interfaces/query-results/results/"><code>Results</code></a> are unchanged, because the predicate is still evaluated for each candidate row. Because the scan limit counts candidate rows, a grouped query that previously exceeded <code>QUERY_WORK_LIMIT_EXCEEDED</code> on a large table may now succeed.</p><p><code>tinyjoin/node</code> no longer fails to start when the parent process runs with a flag that <a href="https://tinyjoin.org/guides/node/">Node</a> rejects for a worker thread, such as the <code>--stack-trace-limit</code> that several test runners set. Inherited flags are dropped rather than the database failing to open.</p><h2 id="v0-1-0">v0.1.0</h2><p>The new <a href="https://tinyjoin.org/guides/node/">Node entry point</a>, <code>tinyjoin/node</code>, opens in-memory databases in <a href="https://tinyjoin.org/guides/node/">Node</a>.js 22 or later. It constructs a Worker thread and loads WASM automatically, returning the same <a href="https://tinyjoin.org/api/tinyjoin/classes/lifecycle/client/"><code>Client</code></a> API without additional dependencies. Each <a href="https://tinyjoin.org/api/tinyjoin/classes/lifecycle/client/"><code>Client</code></a> owns an independent database; filesystem persistence is not included.</p><p><strong>Persistent storage breaks compatibility with v0.0.5.</strong> The npm v0.0.5 release uses page format 1; v0.1.0 uses page format 2. Opening a v0.0.5 database with v0.1.0 fails with <code>UNSUPPORTED_PAGE</code>. There is no automatic migration, and changing the OPFS name does not copy existing data.</p><ul><li>For data that can be reconstructed, use a new OPFS namespace, for example change <code>opfs://my-app-v1</code> to <code>opfs://my-app-v2</code>, and rebuild the database. The old namespace remains intact.</li><li>To retain existing data, export the application&#x27;s known tables using a client pinned to <code>tinyjoin@0.0.5</code> before upgrading. Create the schema in a new namespace with v0.1.0, import rows with parameterized statements, and verify the data before retiring the old database. TinyJoin does not yet provide a general database export or migration API.</li><li>New apps generated by create-tinyjoin v0.1.0 target <code>tinyjoin@^0.1.0</code> and use a <code>-db-v2</code> storage name. Updating the generator does not migrate applications it generated previously.</li></ul><p>This release also makes predicate and assignment type validation consistent across reads and writes, compares heterogeneous JSON values consistently, and bounds shared parameter-graph traversal and expanded SQL bindings before copying values. Append-only transactions now validate new row statements incrementally, including unique-index checks; mixed writes retain complete staged write-set validation.</p><p>Selective multi-table joins now use their actual comparison count rather than a worst-case Cartesian estimate. Scan, build-row, result, memory, and shared script-work limits remain in force.</p><p>Page checksum calculation is faster while preserving the stored checksum values, storage format, and corruption checks. This improves mixed writes and populated startup; the repository&#x27;s <a href="https://github.com/tinyplex/tinyjoin/tree/main/benchmarks">workload measurements</a> retain the before/after samples and runtime hashes.</p><p><code>UPDATE</code> and <code>DELETE</code> now use direct primary-key lookup for exact complete key predicates, including staged transaction rows. Other predicates retain their scan path, and statement validation and constraint checks remain in force.</p><p>Persistent startup avoids a redundant table scan for unique indexes whose columns are all <code>NOT NULL</code>. Table validation and complete index-entry checks remain in force; nullable indexes and indexes without uniqueness retain the existing count scan.</p><p>Duplicate output names in simple projections and <code>RETURNING</code> now fail consistently with <code>INVALID_QUERY</code> before execution. <code>LIMIT</code> and <code>OFFSET</code> reject nonnumeric parameter values consistently in ordinary, aggregate, and join queries, including JSON objects shaped like internal prepared placeholders.</p><p>Persistent Clients now coordinate automatically across tabs and within a page. One elected Worker owns the database; operations, prepared statements, and notifications follow it through handover. Callback transactions exclude other Clients for their duration. In-flight operations interrupted by owner loss reject without automatic replay, and incompatible releases reject explicitly.</p><p>The optional <code>tinyjoin/vite</code> build plugin precaches a complete production application, including lazy Worker, OPFS, and WASM assets. New starter apps enable it by default. Updates wait for old controlled tabs to close; existing service workers can use its generated manifest and helper instead. See the <a href="https://tinyjoin.org/guides/offline/">offline guide</a>.</p><h2 id="v0-0-5">v0.0.5</h2><p>This release establishes TinyJoin as a standalone, SQL-first browser database package.</p><ul><li><a href="https://tinyjoin.org/api/the-essentials/using-a-database/create/"><code>create</code></a>() opens the packaged dedicated Worker and WebAssembly engine with no application Worker boilerplate.</li><li>Memory and persistent OPFS databases use one bounded page-native engine.</li><li>The JavaScript client provides parameterized queries, atomic scripts, callback transactions, reusable prepared statements, and table-level change subscriptions.</li><li>Typed tables support primary keys, maintained secondary and unique indexes, bounded schema additions, aggregates, and left-deep inner and left joins.</li><li><a href="https://tinyjoin.org/api/tinyjoin/interfaces/query-results/results/"><code>Results</code></a> use a familiar <code>rows</code>, <code>fields</code>, <code>affectedRows</code>, <code>command</code>, and <code>rowCount</code> shape, with TinyJoin revision and changed-table metadata.</li><li>The published package includes its runtime, Worker, WASM, declarations, compatibility guide, README, release notes, and agent guidance.</li></ul><p>TinyJoin remains experimental and deliberately smaller than PostgreSQL. This release does not include a PostgreSQL server or wire protocol, hosted service, remote replication, or offline-write synchronization.</p>
