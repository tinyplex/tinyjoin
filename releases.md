<p>This is a reverse chronological summary of TinyJoin releases and their public compatibility boundaries. Every entry states what upgrading to it requires, so check the entries between the version in use and the target before upgrading. A release that needs no action says so explicitly.</p><h2 id="v0-3-0">v0.3.0</h2><p>This release closes some of the most commonly encountered gaps in the <a href="https://tinyjoin.org/guides/sql-compatibility/">SQL dialect</a>. Each form is new syntax that was previously rejected, so an existing statement keeps its meaning.</p><p><code>BETWEEN</code> and <code>NOT BETWEEN</code> are accepted wherever a <code>WHERE</code> clause is, including in aggregates, joins, <code>UPDATE</code>, <code>DELETE</code>, and prepared statements. <code>price BETWEEN $1 AND $2</code> means exactly <code>price &gt;= $1 AND price &lt;= $2</code>, with the same type checking and <code>NULL</code> behavior as those two comparisons, and it is inclusive at both ends. There is no <code>SYMMETRIC</code> form, so a range whose bounds are reversed matches nothing rather than being swapped.</p><p>A single-table <code>SELECT</code> can now rename its columns with <code>AS</code>, as aggregate and join queries already could: <code>SELECT id AS task_id, title FROM tasks</code>. The alias becomes the result field name, <code>ORDER BY</code> can refer to it, and one column may be returned under several names. As in PostgreSQL, an <code>ORDER BY</code> name matches an output alias before a source column of the same name. Output names must still be distinct.</p><p><code>SELECT DISTINCT</code> removes duplicate rows from a single-table or join projection, which is especially useful for collapsing the rows a many-to-many join multiplies, as in <code>SELECT DISTINCT tag.name FROM post_tags JOIN tags AS tag ON post_tags.tag_id = tag.id</code>. <code>NULL</code>s compare as equal to one another, and <code>LIMIT</code> and <code>OFFSET</code> count distinct rows. As in PostgreSQL, <code>ORDER BY</code> must name projected columns. The projection must list its columns explicitly and cannot contain JSON columns or aggregates, and <code>DISTINCT ON</code> and aggregate <code>DISTINCT</code>, such as <code>COUNT(DISTINCT column)</code>, remain unsupported. A column named <code>distinct</code> remains usable.</p><p><code>INSERT ... ON CONFLICT</code> makes an upsert one atomic statement rather than an <code>UPDATE</code> followed by a conditional <code>INSERT</code> inside a transaction, which held every tab sharing the database for the duration. <code>ON CONFLICT (id) DO NOTHING</code> skips conflicting rows, and <code>ON CONFLICT (id) DO UPDATE SET value = EXCLUDED.value</code> rewrites the stored row. The target is the primary key or the columns of one unique index, and <code>DO NOTHING</code> may omit it to treat every unique constraint as an arbiter. Rows are handled one at a time as in PostgreSQL, so a statement that would update the same row twice fails with <code>CONSTRAINT_VIOLATION</code>. <code>SET</code> accepts literals, parameters, <code>DEFAULT</code>, and <code>EXCLUDED</code> columns, but cannot read the existing row or change its primary key, and <code>DO UPDATE ... WHERE</code> is not supported. <code>RETURNING</code>, the row count, and changed keys include only inserted and updated rows, so a statement that skips every row reports no change. See <a href="https://tinyjoin.org/guides/sql-compatibility/#upserts">upserts</a>.</p><p><code>LIKE</code>, <code>ILIKE</code>, and their <code>NOT</code> forms match a text column against a pattern in which <code>%</code> matches any run of characters and <code>_</code> exactly one, so a search box no longer has to filter rows in JavaScript: <code>WHERE title ILIKE $1</code> with <code>&#x27;%&#x27; + term + &#x27;%&#x27;</code>. Backslash escapes a literal <code>%</code> or <code>_</code> unless an <code>ESCAPE</code> clause names another character, and a pattern that ends in its escape character is rejected. A search term from user input should have its own <code>%</code>, <code>_</code>, and backslash characters escaped before being wrapped in wildcards. <code>ILIKE</code> folds only ASCII letters, as PostgreSQL does under the C locale, which is consistent with TinyJoin&#x27;s code-point ordering, so <code>&#x27;É&#x27; ILIKE &#x27;é&#x27;</code> is false. Pattern matching always scans candidate rows rather than using an index.</p><p><strong>Upgrading from v0.2.0 needs no action.</strong> Install, rebuild, and redeploy. The Worker protocol stays at version 8 and the page format stays at format 2, so an existing database opens with no migration and no OPFS namespace change. The new syntax was previously rejected, so statements that already worked keep their results.</p><p>The engine is now built with Rust 1.98.1 rather than 1.91.1. That more than offsets the new SQL, so the compressed WebAssembly engine is about 4 KiB smaller than in v0.2.0.</p><h2 id="v0-2-0">v0.2.0</h2><p>Subscriptions and statement results now report <strong>which rows changed</strong>, not only which tables. A <a href="https://tinyjoin.org/api/tinyjoin/interfaces/subscriptions/tableschangedevent/"><code>TablesChangedEvent</code></a> and every <a href="https://tinyjoin.org/api/tinyjoin/interfaces/query-results/results/"><code>Results</code></a> carry a <code>keys</code> map of table name to the primary keys that changed, so a listener can refresh individual rows instead of re-reading a table. Keys are reported for writes from any connected <a href="https://tinyjoin.org/api/tinyjoin/classes/lifecycle/client/"><code>Client</code></a>, which makes a change made in another tab resolvable to individual rows. See <a href="https://tinyjoin.org/guides/transactions-and-changes/#refreshing-individual-rows">refreshing individual rows</a>.</p><p>Reporting is a bounded best effort, and the changed-table list stays authoritative. A table appears in <code>keys</code> only when every key it changed fits the bound of 1,000 keys per table; a table that changed more rows is absent rather than partially listed, so an absent table means its rows cannot be named and must be re-queried. <code>keys</code> is always empty alongside <code>reset: true</code>. Code that assumes keys are present will silently miss large writes, so handle the absent case.</p><p><strong>The Worker protocol version moves from 7 to 8.</strong> <a href="https://tinyjoin.org/api/tinyjoin/classes/lifecycle/client/"><code>Client</code></a> and Worker ship together and are upgraded together by a normal install, so this affects only a deployment that pins or caches a Worker file independently of the client bundle. A mismatched pair fails cleanly with <code>PROTOCOL_MISMATCH</code> rather than misreading a result. Applications using <a href="https://tinyjoin.org/api/vite/functions/offline/tinyjoinoffline/"><code>tinyjoinOffline()</code></a> are unaffected: the plugin revisions both files by content, so a rebuild replaces them together.</p><p><strong>Upgrading from v0.1.0 needs no action.</strong> Install, rebuild, and redeploy. Persistent storage is unchanged: the page format remains format 2, so an existing database opens with no migration and no OPFS namespace change. The <code>keys</code> field is additive, so application code that ignores it behaves exactly as it did before.</p><p>Grouped and aggregate queries now use a secondary index when their predicate supplies every column of one, instead of always scanning the table. <a href="https://tinyjoin.org/api/tinyjoin/interfaces/query-results/results/"><code>Results</code></a> are unchanged, because the predicate is still evaluated for each candidate row. Because the scan limit counts candidate rows, a grouped query that previously exceeded <code>QUERY_WORK_LIMIT_EXCEEDED</code> on a large table may now succeed.</p><p><code>tinyjoin/node</code> no longer fails to start when the parent process runs with a flag that <a href="https://tinyjoin.org/guides/node/">Node</a> rejects for a worker thread, such as the <code>--stack-trace-limit</code> that several test runners set. Inherited flags are dropped rather than the database failing to open.</p><h2 id="v0-1-0">v0.1.0</h2><p>The new <a href="https://tinyjoin.org/guides/node/">Node entry point</a>, <code>tinyjoin/node</code>, opens in-memory databases in <a href="https://tinyjoin.org/guides/node/">Node</a>.js 22 or later. It constructs a Worker thread and loads WASM automatically, returning the same <a href="https://tinyjoin.org/api/tinyjoin/classes/lifecycle/client/"><code>Client</code></a> API without additional dependencies. Each <a href="https://tinyjoin.org/api/tinyjoin/classes/lifecycle/client/"><code>Client</code></a> owns an independent database; filesystem persistence is not included.</p><p><strong>Persistent storage breaks compatibility with v0.0.5.</strong> The npm v0.0.5 release uses page format 1; v0.1.0 uses page format 2. Opening a v0.0.5 database with v0.1.0 fails with <code>UNSUPPORTED_PAGE</code>. There is no automatic migration, and changing the OPFS name does not copy existing data.</p><ul><li>For data that can be reconstructed, use a new OPFS namespace, for example change <code>opfs://my-app-v1</code> to <code>opfs://my-app-v2</code>, and rebuild the database. The old namespace remains intact.</li><li>To retain existing data, export the application&#x27;s known tables using a client pinned to <code>tinyjoin@0.0.5</code> before upgrading. Create the schema in a new namespace with v0.1.0, import rows with parameterized statements, and verify the data before retiring the old database. TinyJoin does not yet provide a general database export or migration API.</li><li>New apps generated by create-tinyjoin v0.1.0 target <code>tinyjoin@^0.1.0</code> and use a <code>-db-v2</code> storage name. Updating the generator does not migrate applications it generated previously.</li></ul><p>This release also makes predicate and assignment type validation consistent across reads and writes, compares heterogeneous JSON values consistently, and bounds shared parameter-graph traversal and expanded SQL bindings before copying values. Append-only transactions now validate new row statements incrementally, including unique-index checks; mixed writes retain complete staged write-set validation.</p><p>Selective multi-table joins now use their actual comparison count rather than a worst-case Cartesian estimate. Scan, build-row, result, memory, and shared script-work limits remain in force.</p><p>Page checksum calculation is faster while preserving the stored checksum values, storage format, and corruption checks. This improves mixed writes and populated startup; the repository&#x27;s <a href="https://github.com/tinyplex/tinyjoin/tree/main/benchmarks">workload measurements</a> retain the before/after samples and runtime hashes.</p><p><code>UPDATE</code> and <code>DELETE</code> now use direct primary-key lookup for exact complete key predicates, including staged transaction rows. Other predicates retain their scan path, and statement validation and constraint checks remain in force.</p><p>Persistent startup avoids a redundant table scan for unique indexes whose columns are all <code>NOT NULL</code>. Table validation and complete index-entry checks remain in force; nullable indexes and indexes without uniqueness retain the existing count scan.</p><p>Duplicate output names in simple projections and <code>RETURNING</code> now fail consistently with <code>INVALID_QUERY</code> before execution. <code>LIMIT</code> and <code>OFFSET</code> reject nonnumeric parameter values consistently in ordinary, aggregate, and join queries, including JSON objects shaped like internal prepared placeholders.</p><p>Persistent Clients now coordinate automatically across tabs and within a page. One elected Worker owns the database; operations, prepared statements, and notifications follow it through handover. Callback transactions exclude other Clients for their duration. In-flight operations interrupted by owner loss reject without automatic replay, and incompatible releases reject explicitly.</p><p>The optional <code>tinyjoin/vite</code> build plugin precaches a complete production application, including lazy Worker, OPFS, and WASM assets. New starter apps enable it by default. Updates wait for old controlled tabs to close; existing service workers can use its generated manifest and helper instead. See the <a href="https://tinyjoin.org/guides/offline/">offline guide</a>.</p><h2 id="v0-0-5">v0.0.5</h2><p>This release establishes TinyJoin as a standalone, SQL-first browser database package.</p><ul><li><a href="https://tinyjoin.org/api/the-essentials/using-a-database/create/"><code>create</code></a>() opens the packaged dedicated Worker and WebAssembly engine with no application Worker boilerplate.</li><li>Memory and persistent OPFS databases use one bounded page-native engine.</li><li>The JavaScript client provides parameterized queries, atomic scripts, callback transactions, reusable prepared statements, and table-level change subscriptions.</li><li>Typed tables support primary keys, maintained secondary and unique indexes, bounded schema additions, aggregates, and left-deep inner and left joins.</li><li><a href="https://tinyjoin.org/api/tinyjoin/interfaces/query-results/results/"><code>Results</code></a> use a familiar <code>rows</code>, <code>fields</code>, <code>affectedRows</code>, <code>command</code>, and <code>rowCount</code> shape, with TinyJoin revision and changed-table metadata.</li><li>The published package includes its runtime, Worker, WASM, declarations, compatibility guide, README, release notes, and agent guidance.</li></ul><p>TinyJoin remains experimental and deliberately smaller than PostgreSQL. This release does not include a PostgreSQL server or wire protocol, hosted service, remote replication, or offline-write synchronization.</p>
