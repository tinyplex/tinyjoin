<p>This is a reverse chronological summary of TinyJoin releases and their public compatibility boundaries.</p><h2 id="v0-0-6">v0.0.6</h2><p>This release is being prepared locally and has not yet been published.</p><p>The new <a href="https://tinyjoin.org/guides/node/">Node entry point</a>, <code>tinyjoin/node</code>, opens in-memory databases in <a href="https://tinyjoin.org/guides/node/">Node</a>.js 22 or later. It constructs a Worker thread and loads WASM automatically, returning the same <a href="https://tinyjoin.org/api/tinyjoin/classes/lifecycle/client/"><code>Client</code></a> API without additional dependencies. Each <a href="https://tinyjoin.org/api/tinyjoin/classes/lifecycle/client/"><code>Client</code></a> owns an independent database; filesystem persistence is not included.</p><p><strong>Persistent storage breaks compatibility with v0.0.5.</strong> The npm v0.0.5 release uses page format 1; v0.0.6 uses page format 2. Opening a v0.0.5 database with v0.0.6 fails with <code>UNSUPPORTED_PAGE</code>. There is no automatic migration, and changing the OPFS name does not copy existing data.</p><ul><li>For data that can be reconstructed, use a new OPFS namespace, for example change <code>opfs://my-app-v1</code> to <code>opfs://my-app-v2</code>, and rebuild the database. The old namespace remains intact.</li><li>To retain existing data, export the application&#x27;s known tables using a client pinned to <code>tinyjoin@0.0.5</code> before upgrading. Create the schema in a new namespace with v0.0.6, import rows with parameterized statements, and verify the data before retiring the old database. TinyJoin does not yet provide a general database export or migration API.</li><li>New apps generated by create-tinyjoin v0.0.7 target <code>tinyjoin@^0.0.6</code> and use a <code>-db-v2</code> storage name. Updating the generator does not migrate applications it generated previously.</li></ul><p>This release also makes predicate and assignment type validation consistent across reads and writes, compares heterogeneous JSON values consistently, and bounds shared parameter-graph traversal and expanded SQL bindings before copying values. Append-only transactions now validate new row statements incrementally, including unique-index checks; mixed writes retain complete staged write-set validation.</p><p>Selective multi-table joins now use their actual comparison count rather than a worst-case Cartesian estimate. Scan, build-row, result, memory, and shared script-work limits remain in force.</p><p>Page checksum calculation is faster while preserving the stored checksum values, storage format, and corruption checks. This improves mixed writes and populated startup; the repository&#x27;s <a href="https://github.com/tinyplex/tinyjoin/tree/main/benchmarks">workload measurements</a> retain the before/after samples and runtime hashes.</p><p><code>UPDATE</code> and <code>DELETE</code> now use direct primary-key lookup for exact complete key predicates, including staged transaction rows. Other predicates retain their scan path, and statement validation and constraint checks remain in force.</p><p>Persistent startup avoids a redundant table scan for unique indexes whose columns are all <code>NOT NULL</code>. Table validation and complete index-entry checks remain in force; nullable indexes and indexes without uniqueness retain the existing count scan.</p><p>Duplicate output names in simple projections and <code>RETURNING</code> now fail consistently with <code>INVALID_QUERY</code> before execution. <code>LIMIT</code> and <code>OFFSET</code> reject nonnumeric parameter values consistently in ordinary, aggregate, and join queries, including JSON objects shaped like internal prepared placeholders.</p><p>Persistent Clients now coordinate automatically across tabs and within a page. One elected Worker owns the database; operations, prepared statements, and notifications follow it through handover. Callback transactions exclude other Clients for their duration. In-flight operations interrupted by owner loss reject without automatic replay, and incompatible releases reject explicitly.</p><p>The optional <code>tinyjoin/vite</code> build plugin precaches a complete production application, including lazy Worker, OPFS, and WASM assets. New starter apps enable it by default. Updates wait for old controlled tabs to close; existing service workers can use its generated manifest and helper instead. See the <a href="https://tinyjoin.org/guides/offline/">offline guide</a>.</p><h2 id="v0-0-5">v0.0.5</h2><p>This release establishes TinyJoin as a standalone, SQL-first browser database package.</p><ul><li><a href="https://tinyjoin.org/api/the-essentials/using-a-database/create/"><code>create</code></a>() opens the packaged dedicated Worker and WebAssembly engine with no application Worker boilerplate.</li><li>Memory and persistent OPFS databases use one bounded page-native engine.</li><li>The JavaScript client provides parameterized queries, atomic scripts, callback transactions, reusable prepared statements, and table-level change subscriptions.</li><li>Typed tables support primary keys, maintained secondary and unique indexes, bounded schema additions, aggregates, and left-deep inner and left joins.</li><li><a href="https://tinyjoin.org/api/tinyjoin/interfaces/query-results/results/"><code>Results</code></a> use a familiar <code>rows</code>, <code>fields</code>, <code>affectedRows</code>, <code>command</code>, and <code>rowCount</code> shape, with TinyJoin revision and changed-table metadata.</li><li>The published package includes its runtime, Worker, WASM, declarations, compatibility guide, README, release notes, and agent guidance.</li></ul><p>TinyJoin remains experimental and deliberately smaller than PostgreSQL. This release does not include a PostgreSQL server or wire protocol, hosted service, remote replication, or offline-write synchronization.</p>
